AI Workbench user journey

What it is like for an on-call engineer to go from a failed Terraform run to a verified fix, with the triage agent doing the digging and the human keeping the final say. Walked through with the demo sample 01-garage-down.

Who it is for

OperatorAn infra engineer on call for a small self-hosted stack, run with Ansible and Terraform. Knows the systems, but not every past incident.
SituationA pipeline went red. The error says connection refused, which could be network, credentials or a dead service.
What they needThe real cause fast, a fix they can trust, and nothing changed on the system without their say-so.

Journey map

Stages run left to right in the order they happen. The shaded column is the approval gate, the one point where the agent stops and waits for the operator.

Operator does Sees the Ansible play fail at terraform workspace select. Runs agent_demo.py 01-garage-down or sends the log to POST /agent/runs. Reads which runbooks matched, and how closely. Watches each command and its output stream past. Reads the commands, the reason and the risk. Types y, or n with a note. Reads the report; re-runs the pipeline.
Agent does — Pulls the error lines out of the log (fatal, stderr, operator notes). Embeds them with Qwen3-Embedding-8B and searches the runbooks in pgvector. Nemotron Super calls run_diagnostic with read-only commands; the server refuses anything that writes. Calls propose_fix, then stops. Nothing runs until the operator decides. Runs the approved commands, re-checks the host, writes the report.

Without the agent Guesses: network? credentials? The two Terraform errors look alike. SSHes to hosts one by one. Searches chat history for “last time this happened”. A plain LLM, with no runbook, suggests generic fixes, such as editing files the platform overwrites. Copies commands from a chat window with no record of who approved what. Writes the incident note by hand, if at all.

At the approval gate

Approve

The commands run on the host. The agent re-checks with docker ps and docker logs, then reports. If the fix did not work (for example, Garage starts and crashes again), the agent sees it in the check.

Reject with a note

Nothing runs. The note goes back to the agent, for example “not during business hours, write up the steps for tonight”, and the report becomes a hand-off plan instead.

Guardrails the operator never has to think about

Diagnostics are checked against a read-only allowlist on the server. Fixes that delete volumes or data are flagged DESTRUCTIVE. One fix is pending at a time, and a decision cannot be made twice.

How a run flows

sequenceDiagram
    actor Op as Operator
    participant API as Agent API
    participant KB as Runbooks (pgvector)
    participant LLM as Nemotron Super
    participant Host as Host (sandbox)
    Op->>API: failed log
    API->>KB: error lines, embedded
    KB-->>API: matching runbooks
    loop up to 6 diagnostics (3 kept for verifying)
        API->>LLM: log + runbooks + results so far
        LLM-->>API: run_diagnostic(command)
        API->>Host: read-only command (allowlist checked)
        Host-->>API: output
    end
    LLM-->>API: propose_fix(commands, reason, risk)
    API-->>Op: awaiting_approval
    alt approve
        Op->>API: decision: approve
        API->>Host: run fix
        API->>LLM: fix output
        LLM->>Host: verify (read-only)
    else reject
        Op->>API: decision: reject + note
        API->>LLM: note, nothing ran
    end
    LLM-->>API: report
    API-->>Op: cause, what was done, follow-up

Run states

stateDiagram-v2
    [*] --> running: POST /agent/runs
    running --> running: diagnostic or runbook search
    running --> awaiting_approval: propose_fix
    awaiting_approval --> running: approve or reject
    running --> done: final report
    running --> failed: 12 model turns, no report
    done --> [*]
    failed --> [*]

A typical Garage run takes about 6 model turns and about 14k input / 1k output tokens on Nemotron 3 Super via Nebius Token Factory. In the demo, commands run against a simulated host so the run is safe and repeatable.
